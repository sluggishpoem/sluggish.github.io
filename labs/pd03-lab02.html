Lab02: SQL injection vulnerability allowing login bypass

Nivel Apprentice (Aprendiz)
Tipo de SQLi SQLi en formulario de autenticación (Bypass de Login)

Objetivo

Acceder a la aplicación como el usuario administrator sin conocer su contraseña, manipulando la consulta de inicio de sesión.

Vulnerabilidad

El formulario de login toma el nombre de usuario y la contraseña para construir una consulta similar a esta:

SELECT * FROM users WHERE username = '[USUARIO]' AND password = '[PASSWORD]'

Si el atacante ingresa un payload que cierre la comilla del usuario y comente el resto de la consulta, el motor de base de datos solo validará que el usuario exista, ignorando por completo la validación de la contraseña.

Procedimiento

  1. Acceder al laboratorio y navegar al menú de login (esquina superior derecha "My account").
  2. Abrir Burp Suite, activar Proxy e interceptar la petición GET a la página de login.
  3. Intentar un ingreso con el usuario "administrator" y una contraseña cualquiera (ej. "1234"), interceptándose la petición POST en Burp. 
    POST /login HTTP/1.1
...
username=administrator&password=1234
  4. Modificar el payload en el Repeater, cambiando el cuerpo de la petición por: 
    username=administrator'--&password=1234
  5. Enviar la petición y verificar que se obtiene una respuesta 302 Found (redirección), lo que indica que se ha iniciado sesión como administrador.

Payload utilizado

administrator'--

Explicación del payload

  • administrator: Es el nombre de la cuenta objetivo.
  • ' (Comilla): Cierra el campo del nombre de usuario en la consulta SQL.
  • -- (Comentario): Hace que todo lo que sigue (AND password = '...') sea ignorado.

Consulta final ejecutada

SELECT * FROM users WHERE username = 'administrator'--' AND password = '1234'

Como el resto de la consulta después de -- se convierte en comentario, la base de datos simplemente busca al usuario "administrator" y, al encontrarlo, devuelve el registro, permitiendo el acceso sin verificar la contraseña.

Evidencia técnica

Verificación del ataque

Al enviar el payload administrator'--, el servidor responde con un código 302 Found que redirige al panel de administración. Esto confirma que la inyección SQL fue exitosa y que la validación de la contraseña fue neutralizada.

En la interfaz web, se puede observar que se ha iniciado sesión como administrator, pudiendo acceder a funcionalidades restringidas como la gestión de usuarios.

Resultado esperado: El laboratorio se resuelve correctamente y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Consultas Preparadas (Bind Variables)

Nunca concatenar directamente la entrada del usuario en la consulta. Utilizar consultas parametrizadas:

SELECT * FROM users WHERE username = ? AND password = ?

Hashing de contraseñas

Aunque no previene la SQLi, es vital que las contraseñas no se manejen en texto plano. Almacenar siempre hashes seguros (bcrypt, Argon2).

Manejo de errores genérico

No indicar si el error fue en el "usuario" o la "contraseña" para no dar pistas al atacante. Mostrar mensajes genéricos como "Credenciales incorrectas".

Validación de entradas

Implementar listas blancas para los nombres de usuario, permitiendo solo caracteres alfanuméricos.
