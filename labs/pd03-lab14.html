Lab14: Blind SQL injection with time delays

Nivel Practitioner
Tipo de SQLi Blind SQL injection with time delays

Objetivo

Introducir un comando que genere un retraso (delay) en la página para observar si se puede realizar una inyección de SQL basada en tiempo.

Vulnerabilidad

La cookie TrackingId es vulnerable a inyección SQL. La aplicación no muestra cambios en el contenido ni errores, pero permite ejecutar consultas que introducen pausas en la base de datos. Al medir el tiempo de respuesta del servidor, el atacante puede inferir si una condición es verdadera o falsa.

En este laboratorio, el objetivo no es extraer datos, sino simplemente demostrar que es posible introducir un retraso temporal mediante SQL Injection. Esto confirma la vulnerabilidad y prepara el terreno para ataques de extracción basados en tiempo.

Cada motor de base de datos tiene su propia función para generar pausas:

  • PostgreSQL: pg_sleep(segundos)
  • MySQL: SLEEP(segundos)
  • Microsoft SQL Server: WAITFOR DELAY '0:0:10'
  • Oracle: DBMS_LOCK.SLEEP(10) o mediante consultas heavy que consuman tiempo

Procedimiento

  1. Enviar la petición al Repeater de BurpSuite y observar la cookie de TrackingId. 
    GET / HTTP/1.1
Cookie: TrackingId=xyz123
  2. Agregar una comilla al final para terminar la consulta de la cookie e ingresar el operador de concatenación: 
    Cookie: TrackingId=xyz' ||
  3. Probar con diferentes funciones de delay para identificar el motor de base de datos:

    Prueba con SLEEP (MySQL):

    Cookie: TrackingId=xyz' || SLEEP(10)--

    La respuesta es rápida (menos de 1 segundo), indicando que no es MySQL.

    Prueba con pg_sleep (PostgreSQL):

    Cookie: TrackingId=xyz' || pg_sleep(10)--

    La respuesta tarda aproximadamente 10 segundos, confirmando que la base de datos es PostgreSQL.

  4. Verificar el delay observando el tiempo de respuesta en Burp Suite:
    • Sin inyección: tiempo de respuesta ~100-300 ms.
    • Con pg_sleep(10): tiempo de respuesta ~10,000-10,300 ms.
  5. Confirmar la vulnerabilidad al comprobar que el servidor tarda 10 segundos en responder exclusivamente cuando se inyecta pg_sleep(10).

Payload utilizado

xyz' || (SELECT pg_sleep(10))--

Explicación del payload

  • xyz': Cierra la cadena original de la cookie TrackingId.
  • ||: Operador de concatenación en PostgreSQL. Permite agregar el resultado de una subconsulta a la cadena original.
  • (SELECT pg_sleep(10)): Subconsulta que ejecuta la función pg_sleep(10), causando una pausa de 10 segundos en la base de datos.
  • --: Comenta el resto de la consulta original para evitar errores de sintaxis.

Variantes según motor de base de datos

Motor Payload
PostgreSQL ' || (SELECT pg_sleep(10))--
MySQL ' OR SLEEP(10)--
Microsoft SQL Server '; WAITFOR DELAY '0:0:10'--
Oracle ' || (SELECT DBMS_LOCK.SLEEP(10) FROM DUAL)--

Consulta final ejecutada (PostgreSQL)

SELECT * FROM tracking WHERE id = 'xyz' || (SELECT pg_sleep(10))--'

La consulta concatena el resultado de pg_sleep(10) (que es NULL) al valor original, pero lo importante es que la función se ejecuta y causa un retraso de 10 segundos antes de que la consulta complete su ejecución.

Verificación del ataque

La vulnerabilidad se confirma al observar que:

  • La petición con el payload xyz' || (SELECT pg_sleep(10))-- tarda aproximadamente 10 segundos en recibir respuesta.
  • La petición sin inyección o con payloads incorrectos responde inmediatamente.
  • La diferencia en el tiempo de respuesta es consistente y reproducible.

Esto demuestra que es posible ejecutar comandos SQL arbitrarios en el servidor de base de datos, aunque no haya cambios visibles en la página. Esta técnica es la base para ataques de extracción de datos basados en tiempo (time-based blind SQL injection).

Resultado esperado: El laboratorio se resuelve correctamente al introducir el delay y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal. Al usar parámetros, los valores inyectados se tratan como datos y no como parte del código SQL, bloqueando cualquier intento de inyección, incluyendo funciones como pg_sleep().

SELECT * FROM tracking WHERE id = ?

Validación de Entradas

Validar estrictamente el formato del TrackingId. Si sigue un patrón predecible (alfanumérico de longitud fija), rechazar cualquier valor que no cumpla con ese patrón.

Límite de Tiempo de Ejecución

Configurar límites de tiempo de ejecución para las consultas en la base de datos, de modo que funciones como pg_sleep() no puedan ejecutarse o sean interrumpidas.

Principio de Menor Privilegio

La cuenta de base de datos debe tener permisos mínimos. Idealmente, no debería tener permiso para ejecutar funciones como pg_sleep() que no son necesarias para el funcionamiento normal de la aplicación.

Web Application Firewall (WAF)

Implementar un WAF que detecte y bloquee patrones de inyección SQL, incluyendo intentos de usar funciones de delay.

Eliminar la Capacidad de Ejecutar Funciones Peligrosas

En PostgreSQL, se puede revocar el permiso de ejecución de funciones como pg_sleep() para el usuario de la aplicación.
