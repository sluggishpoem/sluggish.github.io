Lab01: SQL injection vulnerability in WHERE clause allowing retrieval of hidden data

Nivel Apprentice (Aprendiz)
Tipo de SQLi SQLi clásica en la cláusula WHERE (Manipulación de lógica booleana)

Objetivo

Modificar la consulta SQL para que la aplicación muestre todos los productos de una categoría específica, incluyendo aquellos que aún no han sido lanzados (released = 0).

Vulnerabilidad

La vulnerabilidad ocurre porque la aplicación concatena directamente la entrada del usuario (el nombre de la categoría) en una consulta SQL sin sanitizarla ni usar consultas preparadas.

La consulta original es:

SELECT * FROM products WHERE category = '[CATEGORÍA]' AND released = 1

Al no haber validación, un atacante puede cerrar la comilla simple del string de la categoría y añadir operadores lógicos (OR) que alteren la condición de la cláusula WHERE, haciendo que siempre devuelva "verdadero" (TRUE) y comentando el resto de la consulta original.

Procedimiento

  1. Acceder al laboratorio e interactuar con el filtro al seleccionar cualquier categoría de la lista (por ejemplo, "Gifts").
  2. Abrir Burp Suite, asegurándose de que el Proxy esté activado e interceptar la petición que se ve así: 
    GET /filter?category=Gifts
  3. Modificar el parámetro enviando la petición al Repeater, cambiando el valor de category (Gifts) por el payload: 
    ' OR 1=1--
  4. Enviar y verificar que la respuesta HTTP 200 contiene muchos más productos de los que se veían originalmente, comprobándose al actualizarse la página.

Payload utilizado

' OR 1=1--

Explicación del payload

  • ' (Comilla simple): Rompe la cadena de texto (string) original en la consulta SQL.
  • OR 1=1: Es una condición que siempre es verdadera. Como se usa el operador OR, no importa si la categoría existe o si released es 1; basta con que 1=1 sea cierto para que la base de datos devuelva todas las filas.
  • -- (Guion guion): Es el carácter de comentario en SQL (específicamente para bases de datos como PostgreSQL o MySQL). Esto hace que el resto de la consulta original (' AND released = 1) sea ignorado por el motor de base de datos.

Consulta final ejecutada

SELECT * FROM products WHERE category = '' OR 1=1--' AND released = 1

Todo lo que sigue a -- se convierte en comentario, por lo que la condición AND released = 1 es ignorada.

Verificación del ataque

Al enviar el payload ' OR 1=1--, la aplicación muestra productos adicionales que antes estaban ocultos (aquellos con released = 0). Esto confirma que la inyección SQL fue exitosa y que la condición AND released = 1 fue neutralizada.

La respuesta HTTP 200 contiene un número significativamente mayor de productos en comparación con la solicitud original sin modificar, demostrando que la consulta SQL fue alterada exitosamente.

Resultado esperado: El laboratorio se resuelve correctamente y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

La forma más efectiva de prevenir este ataque es dejar de concatenar strings y utilizar Consultas Preparadas (Parameterized Queries).

En lugar de construir la query manualmente, se define una estructura fija:

SELECT * FROM products WHERE category = ? AND released = 1

El valor del usuario se pasa como un parámetro aislado, lo que impide que el motor de base de datos interprete caracteres especiales como ' o -- como parte de la lógica de ejecución.

Otras medidas de defensa:

  • Validación de entradas: Permitir solo caracteres y formatos esperados (lista blanca).
  • Principio de menor privilegio: La cuenta de base de datos debe tener permisos mínimos.
  • Escapado de caracteres especiales: Aunque menos recomendado que las consultas preparadas, puede servir como defensa adicional.
  • Uso de procedimientos almacenados: Implementados de forma segura, sin concatenación interna.
